# 文档与代码同步

改动代码后，必须同步更新文档并一起提交，不要留到下次。这个项目的文档已经因为脱节坑过一次：
`部署说明.md` 里写着 `curl -X POST /api/analysis/refresh` 这类早就删掉的接口，照着做只会拿到 404。

## 什么改动需要动文档

| 改了什么 | 要同步的地方 |
| --- | --- |
| 增删接口、改路径或参数 | `部署说明.md` 第 6 节接口速查、`README.md` 主要接口 |
| 增删定时任务、改频率 | `部署说明.md` 第 7 节 |
| 增删顶层目录或关键模块 | `部署说明.md` 第 8 节目录速查 |
| 改部署流程、脚本、环境变量 | `部署说明.md` 第 2、3 节 |
| 增删数据库表或字段 | `部署说明.md` 第 8 节表清单，迁移方式写清楚 |
| 换数据源、改兜底策略 | `README.md` 数据来源、`部署说明.md` 第 1 节 |
| 删掉某个功能 | 两份文档里所有相关描述，别只删一半 |

## 写文档的要求

- **只写验证过的事实。** 命令要实际跑过，接口清单从代码里取（例如遍历 `app.routes`），不要凭记忆写。
- **记录踩过的坑和反直觉的地方**，这比罗列功能有用。例如货币基金的 `NAV` 字段其实是万份收益、
  push2 会断连所以必须三级兜底、15:00–15:10 这段 `session_label()` 显示已收盘但仍要轮询。
- **已知故障要写进文档**，不要假装一切正常。例如当前 `https://ohmygold.icu` 的 TLS 握手被重置。
- 不写空话和重复段落。文档长度要和实际内容相称。

## 提交

- 文档改动和对应的代码改动放在**同一个提交**里，不要单独补一个「更新文档」的提交。
- 用户要求上传时才 `git push`，但文档该改的必须已经改好、已经 `git add`。
- 提交信息里说明行为变化和原因，尤其是删除功能时说清为什么可以删、什么被保留。

## 别漏掉的连带物

删功能时，除了代码还要检查这些地方有没有变成死物，有就一并处理或明确告知用户：

- `backend/scripts/` 下的脚本是否还 import 得到
- `miniprogram/` 调用的接口是否还存在
- `docker-compose.yml` 里的环境变量是否还绑定到 `Settings` 字段
- `frontend/package.json` 里是否有依赖已无人使用（删了要同步 `package-lock.json`，
  Dockerfile 用 `npm ci`，lock 不同步会让镜像构建失败）
- `config.py` 里是否留下没人引用的配置项
